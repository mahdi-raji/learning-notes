## ۱. ایده اصلی فصل

موضوع اصلی فصل چهارم اینه که:

وقتی ساختار داده‌ها یا کد نرم‌افزار تغییر می‌کنه، چطور کاری کنیم نسخه‌های قدیمی و جدید همچنان بتونن با هم کار کنن؟

فرض کن نسخه اول یک نرم‌افزار این اطلاعات رو ذخیره می‌کنه:

```
{
  "id": 100,
  "name": "Ali"
}
```

در نسخه دوم یک فیلد جدید اضافه می‌کنیم:

```
{
  "id": 100,
  "name": "Ali",
  "age": 25
}
```

حالا دو سؤال مهم داریم:

- آیا نسخه جدید می‌تونه داده‌های قدیمی رو بخونه؟
    
- آیا نسخه قدیمی می‌تونه داده‌های جدید رو بخونه؟
    

این دو سؤال اساس فصل چهارم هستن.

## ۲. سازگاری نسخه‌ها (Compatibility)

|مفهوم|معنی|
|---|---|
|Backward Compatibility|کد جدید بتونه داده‌های تولیدشده توسط نسخه قدیمی رو بخونه|
|Forward Compatibility|کد قدیمی بتونه داده‌های تولیدشده توسط نسخه جدید رو بخونه|

مثال:

فرض کن نسخه دوم فیلد `age` رو اضافه کرده.

اگر نسخه اول بتونه بدون خطا فیلد ناشناخته `age` رو نادیده بگیره، از نظر خواندن اون داده، Forward Compatibility داریم.

اگر نسخه دوم بتونه داده‌ای رو که اصلاً `age` نداره بخونه، Backward Compatibility داریم.

نکته مهم: سازگاری در سطح فرمت داده لزوماً به معنی سازگاری منطق نرم‌افزار نیست.

ممکنه نسخه قدیمی اطلاعات جدید رو بدون خطا بخونه، ولی چون از مفهوم اون فیلد خبر نداره، محاسبه اشتباهی انجام بده.

## ۳. Encoding و Decoding

وقتی داده‌ها داخل حافظه برنامه هستن، معمولاً به‌شکل Object، Array، String و سایر ساختارهای زبان برنامه‌نویسی نمایش داده می‌شن.

اما برای ذخیره در فایل، دیتابیس یا ارسال از شبکه، باید داده رو به فرمتی قابل انتقال تبدیل کنیم.

Object در حافظه

Encoding / Serialization

JSON / Binary Data

Decoding / Deserialization

Object در برنامه گیرنده

Encoding یعنی تبدیل داده به فرمتی برای ذخیره یا انتقال.

Decoding یعنی بازسازی داده از اون فرمت.

در فصل چهارم، سه خانواده مهم فرمت‌ها بررسی می‌شن.

## ۴. فرمت‌های Encoding

### JSON، XML و CSV

این‌ها فرمت‌های متنی هستن.

مزیت اصلی JSON، خوانایی و پشتیبانی گسترده در زبان‌های برنامه‌نویسیه.

اما محدودیت‌هایی داره؛ مثلاً:

- نوع عدد همیشه به‌شکل دقیق و یکسان بین زبان‌ها تفسیر نمی‌شه.
    
- JavaScript اعداد صحیح رو با نوع معمول `Number` فقط تا `2^53 - 1` به‌شکل دقیق تضمین می‌کنه.
    
- JSON به‌خودی‌خود Schema اجباری نداره.
    
- تکرار نام فیلدها می‌تونه حجم داده رو افزایش بده.
    

### Protocol Buffers و Thrift

این فرمت‌ها داده‌ها رو به‌شکل Binary و با استفاده از Schema مشخص کدگذاری می‌کنن.

مثلاً در Protocol Buffers:

```
message User {
  int32 id = 1;
  string name = 2;
  int32 age = 3;
}
```

مهم‌ترین نکته اینه که هر فیلد یک شماره مشخص داره.

در داده باینری معمولاً نام فیلد ذخیره نمی‌شه؛ شماره فیلد و اطلاعات نوع و مقدار اون برای خواندن استفاده می‌شن.

برای Schema Evolution:

- می‌تونیم فیلد جدید اضافه کنیم.
    
- خواننده قدیمی معمولاً می‌تونه فیلد ناشناخته رو رد کنه.
    
- نباید شماره یک فیلد حذف‌شده رو برای معنای متفاوت دوباره استفاده کنیم.
    
- تغییر نام یک فیلد با حفظ شماره، معمولاً سازگاری باینری رو حفظ می‌کنه، اما ممکنه کد تولیدشده یا نمایش JSON رو تحت تأثیر قرار بده.
    

جمع‌بندی: شماره فیلد در Protobuf از اسم فیلد برای سازگاری باینری مهم‌تره.

### Apache Avro

Avro هم یک فرمت Binary مبتنی بر Schema هست، ولی تفاوت مهمی با Protobuf داره.

در داده خام Binary مربوط به یک Record، Avro معمولاً نه نام فیلد رو ذخیره می‌کنه و نه شماره فیلد رو.

در عوض مقادیر طبق ترتیب Writer Schema نوشته می‌شن.

فرض کن Writer Schema این باشه:

```
id: int
name: string
```

Reader برای تفسیر درست بایت‌ها باید Writer Schema رو بشناسه.

بعد می‌تونه Writer Schema رو با Reader Schema خودش تطبیق بده.

|موضوع|Protocol Buffers|Apache Avro|
|---|---|---|
|شناسایی فیلد|شماره فیلد|نام فیلد در تطبیق Schema|
|ترتیب فیلدها در داده|معمولاً اهمیت نداره|طبق Writer Schema|
|نیاز Reader به Schema نویسنده|معمولاً نه، در قالب عادی Protobuf|بله، برای تفسیر درست بایت‌های خام|
|تغییر نام فیلد|شماره ثابت می‌مونه|ممکنه به Alias نیاز داشته باشه|
|افزودن فیلد|با رعایت قواعد سازگاری|با رعایت قواعد Schema Resolution و مقدار پیش‌فرض مناسب|

در Avro، Writer Schema می‌تونه از طریق Header فایل، Schema Registry یا توافق قبلی در اختیار Reader قرار بگیره.

نکته‌ای که باید یادمون بمونه: صرفاً دریافت بایت‌های Avro برای تفسیر درست اون‌ها کافی نیست؛ Reader باید بدونه Writer با چه Schemaای داده رو نوشته.

کتاب سه مسیر اصلی جریان داده رو بررسی می‌کنه.

۱. Dataflow Through Databases

۲. Dataflow Through Services

سرویس‌ها از طریق API و درخواست/پاسخ با هم ارتباط برقرار می‌کنن.

۳. Dataflow Through Message Passing

برنامه‌ها یا Actorها پیام ارسال و دریافت می‌کنن.

### مسیر اول: دیتابیس

فرض کن نسخه جدید نرم‌افزار فیلد `age` رو به اطلاعات کاربر اضافه کرده.

اما هنوز یک سرور با نسخه قدیمی در حال اجراست.

نسخه قدیمی داده رو می‌خونه، تغییر کوچکی اعمال می‌کنه و کل رکورد رو با نسخه‌ای که خودش می‌شناسه جایگزین می‌کنه.

ممکنه فیلد جدید `age` حذف بشه!

بنابراین مسئله فقط خواندن داده‌های جدید نیست؛ نسخه قدیمی نباید هنگام نوشتن، اطلاعات ناشناخته رو ناخواسته از بین ببره.

این موضوع در Rolling Upgrade اهمیت زیادی داره، چون معمولاً برای مدتی نسخه‌های مختلف نرم‌افزار هم‌زمان اجرا می‌شن.

## ۶. مسیر دوم: ارتباط بین سرویس‌ها

### REST

REST یک سبک معماری برای طراحی ارتباط با منابع هست که معمولاً روی HTTP پیاده‌سازی می‌شه.

مثلاً:

```
GET /users/100
```

و پاسخ:

```
{
  "id": 100,
  "name": "Ali"
}
```

در این مدل، سرویس‌ها از طریق درخواست و پاسخ ارتباط برقرار می‌کنن.

اما دو نکته مهم وجود داره:

- ارتباط شبکه‌ای ممکنه قطع بشه.
    
- نسخه Client و Server ممکنه متفاوت باشه.
    

بنابراین باید هم سازگاری داده‌ها و هم رفتار خطاها رو در نظر بگیریم.

### RPC و gRPC

در RPC تلاش می‌کنیم یک عملیات روی سرویس دیگه رو شبیه فراخوانی متد انجام بدیم.

مثلاً:

```
var user = await client.GetUserAsync(request);
```

gRPC یک فریم‌ورک RPC هست که معمولاً از Protocol Buffers برای قرارداد و سریال‌سازی و از HTTP/2 برای انتقال استفاده می‌کنه.

چهار نوع ارتباط مهم gRPC:

|نوع|توضیح|
|---|---|
|Unary|یک درخواست و یک پاسخ|
|Server Streaming|یک درخواست و چند پاسخ از سمت سرور|
|Client Streaming|چند پیام از کلاینت و یک پاسخ|
|Bidirectional Streaming|ارسال و دریافت جریان پیام از هر دو سمت|

نکته اساسی: فراخوانی RPC با فراخوانی متد محلی یکسان نیست.

ممکنه درخواست در سرور اجرا شده باشه، ولی پاسخ به کلاینت نرسه.

در این شرایط، Retry بدون توجه به Idempotency می‌تونه عملیات رو تکرار کنه.

## ۷. مسیر سوم: Message Passing

در این مدل، به‌جای اینکه همیشه یک سرویس مستقیماً سرویس دیگه رو صدا بزنه، می‌تونیم از پیام استفاده کنیم.

### Message Broker

Producer

Message Broker

صف‌بندی و تحویل پیام‌ها

Consumer

Broker می‌تونه بین تولیدکننده و مصرف‌کننده پیام واسطه بشه.

مزیت‌های مهم این مدل:

- Producer لازم نیست همیشه منتظر پایان پردازش Consumer بمونه.
    
- با تنظیمات مناسب، پیام‌ها می‌تونن در زمان قطعی Consumer نگهداری بشن.
    
- می‌تونیم پیام‌ها رو بین چند Consumer توزیع کنیم.
    
- امکان مدیریت اختلاف بین سرعت تولید و مصرف پیام وجود داره.
    

اما Broker تضمین نمی‌کنه که کل مسیر از منبع اولیه تا نتیجه نهایی بدون خطا باشه.

### تضمین‌های تحویل پیام

|روش|رفتار|
|---|---|
|At-Most-Once|پیام ممکنه از دست بره، ولی دوباره تحویل داده نمی‌شه|
|At-Least-Once|پیام با سازوکار تحویل مجدد ممکنه چند بار تحویل داده بشه|
|Exactly-Once Effect|عملیات طوری طراحی می‌شه که با وجود تحویل تکراری، اثر نهایی فقط یک بار ثبت بشه|

برای رسیدن به Exactly-Once Effect معمولاً از Idempotency، شناسه یکتای پیام و تراکنش مناسب استفاده می‌کنیم.

مثلاً اگر یک پیام دو بار دریافت بشه، Consumer نباید دو رکورد یکسان در دیتابیس ایجاد کنه.

## ۸. Actor Model

Actor Model هم از مدل‌های ارتباط مبتنی بر پیام هست.

تفاوتش با Message Broker اینه که Actor خودش یک موجودیت منطقی با هویت و State اختصاصی داره.

هر Actor:

- یک شناسه مشخص داره.
    
- پیام دریافت می‌کنه.
    
- می‌تونه وضعیت داخلی خودش رو تغییر بده.
    
- می‌تونه برای Actorهای دیگه پیام ارسال کنه.
    

در مدل رایج Actor، پیام‌های مربوط به State یک Actor به‌صورت هماهنگ پردازش می‌شن؛ درحالی‌که Actorهای مستقل می‌تونن هم‌زمان فعالیت کنن.

Actor(100)

Actor(200)

State مستقل

ارتباط از طریق پیام

Actor Model بیشتر یک مدل طراحی و اجرای نرم‌افزار هست، نه جایگزین مستقیم REST یا gRPC.

همچنین Actor الزاماً معادل یک Thread یا یک سرور نیست.

### ارتباط Actor Model با موضوع فصل

Actorها ممکنه روی پردازش‌ها یا سرورهای متفاوت اجرا بشن و حتی نسخه‌های متفاوتی از نرم‌افزار داشته باشن.

پس پیام‌های بین Actorها هم با مسئله Encoding، Decoding و Schema Evolution روبه‌رو هستن.

این دلیل اصلی مطرح شدن Actor Model در فصل چهارمه.

## ۱۰. جمع‌بندی نهایی فصل

اگر بخوای کل فصل چهارم رو در چند مفهوم مهم نگه داری، این‌ها هستن:

داده‌ها معمولاً عمر بیشتری از نسخه فعلی کد دارن.

نسخه‌های بعدی باید بتونن داده‌های قدیمی رو بخونن.

تغییر Schema باید با سازگاری نسخه‌ها همراه باشه.

Backward و Forward Compatibility مهم هستن.

فرمت Encoding روی سازگاری تأثیر می‌ذاره.

JSON، Protobuf و Avro قواعد و محدودیت‌های متفاوتی دارن.

جریان داده فقط ارتباط HTTP نیست.

داده از طریق دیتابیس، سرویس‌ها و پیام‌ها بین نسخه‌های مختلف جریان پیدا می‌کنه.

سازگاری فنی با سازگاری منطقی فرق داره.

اینکه یک پیام بدون خطا Decode بشه، تضمین نمی‌کنه برنامه معنای اون رو درست پردازش کنه.

مهم‌ترین جمله برای به خاطر سپردن فصل چهارم:

در یک سیستم واقعی، نمی‌تونیم فرض کنیم همه داده‌ها، همه سرویس‌ها و همه پیام‌ها همیشه با یک نسخه واحد از نرم‌افزار تولید و مصرف می‌شن. طراحی درست باید اجازه بده نسخه‌های مختلف برای مدتی در کنار هم کار کنن.
