**سؤال اصلی فصل:** دیتابیس چطور اطلاعات رو روی دیسک ذخیره می‌کنه، چطور سریع پیداشون می‌کنه و چرا ساختارهای مختلف برای خواندن و نوشتن عملکرد متفاوتی دارن؟

## ۱. مبانی ذخیره‌سازی: RAM، SSD و Page

داده‌ها در نهایت به شکل بایت ذخیره می‌شن.

- **RAM:** حافظه سریع و موقت که دیتابیس برای پردازش و نگهداری داده‌های پرکاربرد استفاده می‌کنه.
- **SSD:** حافظه پایدار که داده‌ها بعد از خاموش شدن سیستم در اون باقی می‌مونن.
- **Offset:** موقعیت یک بایت نسبت به ابتدای فایل.
- **Page:** واحدی از داده که موتور دیتابیس مدیریت می‌کنه؛ مثلاً Pageهای داده در SQL Server معمولاً ۸ کیلوبایت هستن.
- **Sequential I/O:** خواندن یا نوشتن داده‌ها در موقعیت‌های پشت سر هم.
- **Random I/O:** دسترسی به موقعیت‌های پراکنده فایل.

نکته مهم: سرعت دیتابیس فقط به سرعت CPU بستگی نداره. تعداد Pageهایی که باید خوانده یا نوشته بشن هم بسیار مهمه.

## ۲. Append-only Log و Hash Index

فرض کن یک دیتابیس خیلی ساده داریم:

```text
Set(10, "Ali")
Set(20, "Reza")
Set(30, "Sara")
```

می‌تونیم داده‌ها رو پشت سر هم داخل یک فایل بنویسیم:

```text
database.log
------------
10,Ali
20,Reza
30,Sara
```

اما برای اجرای `Get(20)` بدون Index باید فایل رو جست‌وجو کنیم.

برای حل مشکل، یک Hash Index در RAM نگه می‌داریم:

```text
Key → Offset

10 → 0
20 → 7
30 → 15
```

حالا می‌تونیم با استفاده از Offset مستقیماً به موقعیت رکورد برسیم.

اگر مقدار کلید ۲۰ تغییر کنه، به جای بازنویسی داده قدیمی می‌تونیم نسخه جدید رو به انتهای فایل اضافه کنیم و Index رو به‌روز کنیم.

**Compaction** هم نسخه‌های قدیمی و غیرضروری رو حذف می‌کنه تا فایل بی‌دلیل بزرگ نشه.

## ۳. ساختار LSM-Tree

مخفف **Log-Structured Merge Tree** هست.

ایده اصلیش اینه که به جای تغییر دائمی داده‌های پراکنده روی دیسک، تغییرات رو جمع‌آوری و به‌صورت مرتب و دسته‌ای ذخیره کنیم.

```text
                  INSERT / UPDATE
                         |
               +---------+---------+
               |                   |
              WAL               MemTable
     (ثبت تغییر برای بازیابی) (داده‌های مرتب در RAM)
                                   |
                                   v
                             SSTable روی SSD
                          (فایل مرتب و پایدار)
                                   |
                                   v
                           Merge / Compaction
                   (ترکیب فایل‌ها و حذف نسخه‌های قدیمی)
```

**Bloom Filter** ساختار کمکی LSM هست که می‌تونه با هزینه خیلی کم تشخیص بده یک کلید قطعاً در SSTable وجود نداره یا احتمالاً وجود داره. در حالت دوم ممکنه False Positive رخ بده.

## ۴. ساختار B-Tree و B+Tree

B+Tree داده‌ها رو در یک درخت متوازن سازمان‌دهی می‌کنه.

```text
              Root
             [20 | 40]
            /    |    \
           /     |     \
       [5,10] [20,30] [40,50]
         Leaf   Leaf    Leaf
```

در B+Tree:

- Root و Internal Nodeها کلیدهای راهنما و اشاره‌گرهای فرزندان رو دارن.
- Leafها داده‌ها یا ارجاع به رکوردها رو نگه می‌دارن.
- همه Leafها در یک عمق قرار دارن.
- هنگام پر شدن Page ممکنه **Page Split** رخ بده.

در SQL Server، Indexهای ردیفی از خانواده B+Tree هستن.

**Clustered Index:** سطح برگ شامل ردیف‌های اصلی جدول می‌شه.

**Nonclustered Index:** یک ساختار جداست که کلیدهای Index و اطلاعات لازم برای پیدا کردن ردیف‌ها رو نگه می‌داره؛ ممکنه ستون‌های اضافی هم داشته باشه.

### مقایسه B+Tree با LSM-Tree

| ویژگی | B+Tree | LSM-Tree |
|---|---|---|
| روش اصلی تغییر داده | تغییر Pageهای درخت | ثبت تغییر و ساخت فایل‌های مرتب جدید |
| نوشتن | ممکنه پراکنده باشه | عمدتاً دسته‌ای و ترتیبی |
| خواندن | پیمایش درخت | بررسی MemTable و SSTableهای مرتبط |
| هزینه اضافی | Page Split و نگهداری درخت | Compaction و بررسی چند فایل |
| نقطه قوت رایج | جست‌وجوی نقطه‌ای و بازه‌ای | بارهای کاری با نوشتن زیاد |

هیچ‌کدوم همیشه بهتر از دیگری نیستن.

## ۵. WAL، Dirty Page و Checkpoint

این بخش درباره دوام اطلاعات و بازیابی بعد از خرابی بود.

فرض کن:

```sql
UPDATE Users SET Age = 31 WHERE Id = 20;
```

SQL Server صفحه مربوطه رو در RAM تغییر می‌ده. به Page تغییریافته‌ای که هنوز نسخه جدیدش روی فایل داده نوشته نشده، **Dirty Page** می‌گیم.

با مکانیزم **WAL (Write-Ahead Log)**، اطلاعات لازم برای تغییر قبل از نوشتن Page اصلی روی دیسک، به شکل پایدار در Log ثبت می‌شن.

پس ممکنه تراکنش Commit شده باشه اما Page اصلی هنوز روی SSD به‌روز نشده باشه.

**Checkpoint** به نوشتن Dirty Pageها روی دیسک و محدود کردن کار بازیابی کمک می‌کنه.

بعد از Crash هم دو عملیات مهم داریم:

| عملیات | هدف |
|---|---|
| REDO | اعمال تغییرات لازم برای بازیابی وضعیت درست |
| UNDO | برگردوندن تغییرات تراکنش‌های ناتمام |

نکته: در حالت عادی تغییرات از Pageهای RAM به Data File نوشته می‌شن؛ Transaction Log قرار نیست همیشه دوباره خوانده بشه تا Pageها به‌روز بشن.

## ۶. تفاوت OLTP و OLAP

دو نوع نیاز متفاوت از دیتابیس داریم.

**OLTP:** عملیات روزمره مثل ثبت بارنامه، دریافت یک رکورد، تغییر وضعیت پرونده و پرداخت.

**OLAP:** تحلیل حجم بزرگی از اطلاعات مثل مجموع کرایه‌ها به تفکیک استان، ماه یا نوع ناوگان.

| | OLTP | OLAP |
|---|---|---|
| تعداد رکوردهای هر عملیات | معمولاً کم | معمولاً زیاد |
| نوع کار | ثبت، خواندن و تغییر | تحلیل و تجمیع |
| ساختار رایج | Row-oriented و B+Tree | Column-oriented و مدل‌های تحلیلی |
| نمونه | `WHERE Id = 100` | `GROUP BY ProvinceId` |

## ۷. ذخیره‌سازی ستونی یا Columnstore

در ذخیره‌سازی ردیفی، اطلاعات هر رکورد کنار هم قرار دارن:

```text
Row 1: [93, 100]
Row 2: [40, 200]
Row 3: [93, 300]
```

اما در ذخیره‌سازی ستونی:

```text
ProvinceId = [93, 40, 93]
Amount     = [100, 200, 300]
```

ارتباط مقادیر از طریق موقعیت منطقی اون‌ها حفظ می‌شه.

مزیت‌ها:

- برای گزارش‌ها فقط ستون‌های موردنیاز خوانده می‌شن.
- داده‌های مشابه بهتر فشرده می‌شن.
- پردازش دسته‌ای حجم زیادی از اطلاعات کارآمدتر می‌شه.

در SQL Server مفاهیمی مثل `Rowgroup`، `Column Segment` و `Delta Store` هم برای پیاده‌سازی Columnstore استفاده می‌شن.

روش‌های فشرده‌سازی مثل **RLE، Dictionary Encoding و Bit Packing** کمک می‌کنن حجم داده کمتر بشه.

## ۸. Data Warehouse و Star Schema

**Data Warehouse** محیطی برای سازمان‌دهی داده‌های تحلیلی و تاریخی هست که معمولاً از دیتابیس عملیاتی جدا نگهداری می‌شه.

در **Star Schema** دو نوع جدول داریم:

- **Fact:** رویدادها، اندازه‌گیری‌ها و مقادیری مثل مبلغ یا وزن رو نگه می‌داره.
- **Dimension:** اطلاعات توصیفی مثل نام استان، کالا، ناوگان و تاریخ رو نگه می‌داره.

مثلاً:

```text
         DimProduct
              |
DimDate — FactWaybill — DimProvince
              |
          DimVehicle
```

در مقابل، **Snowflake Schema** بعضی Dimensionها رو به جدول‌های نرمال‌شده بیشتری تقسیم می‌کنه.

### مفهوم Grain

Grain یعنی **هر ردیف Fact دقیقاً نماینده چه چیزی هست؟**

مثلاً:

- یک ردیف برای هر بارنامه
- یک ردیف برای هر قلم کالا در یک بارنامه
- یک ردیف برای مجموع بارنامه‌های هر استان در هر روز

انتخاب Grain خیلی مهمه؛ چون اگر مبلغ کل یک بارنامه رو در تمام اقلام اون تکرار کنیم، هنگام جمع‌زدن ممکنه مبلغ چند برابر شمرده بشه.

## ۹. Materialized View و Data Cube

**Materialized View** نتیجه یک محاسبه رو از قبل ذخیره می‌کنه.

مثلاً به جای اینکه مرتب روی میلیون‌ها بارنامه `SUM(Amount)` اجرا کنیم، مجموع استان‌ها رو ذخیره می‌کنیم و در صورت تغییر داده‌ها، نتیجه رو به‌روزرسانی می‌کنیم.

در SQL Server، `Indexed View` یک پیاده‌سازی مرتبط با این ایده است.

**Data Cube** هم تحلیل داده براساس ترکیب‌های مختلف ابعاد رو مطرح می‌کنه؛ مثلاً مجموع مبلغ به تفکیک استان، ماه، ناوگان یا ترکیب این سه.

نکته مهم: محاسبه Cube الزاماً به معنی ذخیره کردن نتیجه نیست؛ برای ذخیره‌سازی نتایج باید سازوکار جداگانه‌ای در نظر گرفت.

## نقشه ذهنی کل فصل

**داده‌ها را چطور ذخیره و بازیابی کنیم؟**

| سیستم‌های عملیاتی | سیستم‌های تحلیلی |
|---|---|
| Hash Index | Data Warehouse |
| LSM-Tree | Star Schema |
| B+Tree | Columnstore |
| WAL و Recovery | Materialized View و Cube |

### مهم‌ترین چیزی که باید از این فصل یاد گرفته باشی

این فصل نمی‌خواد فقط چند نوع Index معرفی کنه؛ می‌خواد یاد بده **ساختار ذخیره‌سازی روی هزینه خواندن، نوشتن، بازیابی و تحلیل داده‌ها تأثیر مستقیم داره.**

برای مثال:

- اگر دنبال یک رکورد مشخص باشیم، دسترسی سریع از طریق Index اهمیت زیادی داره.
- اگر مرتب داده‌های جدید وارد کنیم، هزینه نوشتن و مدیریت فایل‌ها مهم می‌شه.
- اگر میلیون‌ها رکورد رو تحلیل کنیم، حجم داده‌ای که باید خوانده بشه اهمیت پیدا می‌کنه.
- اگر بخوایم نتیجه گزارش‌ها سریع آماده باشه، ممکنه هزینه پیش‌محاسبه و نگهداری اون‌ها رو بپذیریم.

**جمع‌بندی فصل در یک جمله:** هیچ ساختار ذخیره‌سازی‌ای برای تمام نیازها بهترین نیست؛ باید براساس الگوی خواندن، نوشتن، حجم داده و نیاز به بازیابی، طراحی مناسب رو انتخاب کنیم.
